# 여러 인스턴스는 공유 볼륨의 SQLite 파일 하나와 Redis 메시지 버스를 함께 쓴다

로컬 오토스케일(5단계)에서 인스턴스가 늘고 줄어도 상태가 남도록, 영속 데이터(회원·세션·방송·댓글·후원)는 **한 노드의 공유 볼륨(PVC)에 둔 SQLite 파일 하나**를 모든 인스턴스가 함께 쓰고, 인스턴스 메모리에만 있던 실시간 상태(라이브 시그널링 방, 댓글·후원 알림, 송출자 접속 여부)는 **Redis pub/sub 와 TTL 키**로 옮겼다. 업로드 영상도 같은 공유 볼륨에 둔다. SQLite 는 같은 호스트의 여러 프로세스가 한 파일을 쓰는 것을 파일 잠금으로 지원하므로(WAL + busy_timeout) 단일 노드 클러스터에서는 안전하고, 1~4단계의 동기 저장소 코드와 테스트를 그대로 유지할 수 있다.

## Considered Options

- **PostgreSQL 로 이전**: 여러 노드에서도 안전한 정석이지만, 모든 저장소·서비스·라우터를 비동기로 바꿔야 하고 1~4단계 테스트가 DB 서버 없이는 돌지 않게 된다. 로컬 단일 노드(k3d)와 다음 단계의 단일 서버(OCI K3s)에서는 이득이 작아 미뤘다.
- **라이브를 같은 인스턴스로 고정 라우팅(sticky)**: 인그레스에서 라이브 ID 별로 한 인스턴스에 묶으면 Redis 없이 시그널링이 되지만, 스케일 인 때 그 인스턴스가 사라지면 결국 끊기고 댓글·후원 알림은 여전히 인스턴스 사이로 전달해야 한다.

## Consequences

- **노드가 둘 이상이 되면 이 결정을 다시 열어야 한다.** SQLite 파일을 네트워크 파일 시스템(NFS 등)이나 여러 노드에서 공유하면 잠금이 보장되지 않는다. 그때는 PostgreSQL 로 옮기고 업로드는 오브젝트 스토리지로 옮긴다.
- 인스턴스가 시작될 때 "방송 중인 라이브를 모두 종료"하던 규칙은 없앴다(새 인스턴스가 뜰 때마다 남의 라이브가 끝나므로). 대신 송출자 접속 표시(Redis TTL 키)가 사라진 지 유예 시간이 지난 라이브를 어느 인스턴스든 주기적으로 종료한다.
- `REDIS_URL` 이 없으면(`npm start` 단일 인스턴스, 테스트) 같은 인터페이스의 메모리 버스를 쓴다.
